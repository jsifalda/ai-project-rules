# Remote MCP Failure Prevention

Use this reference when a remote MCP server exposes authenticated application capabilities.

| Trap | Failure | Prevention | Proof |
| --- | --- | --- | --- |
| Validation trusts types | A cast or parsed-looking object lets invalid or privileged input reach a service. | Validate every tool input at runtime before business logic. Derive the authenticated subject from the access token, never from tool input. Keep tools as thin adapters over an audited service boundary. | Send malformed input and an input body that names another user. Confirm both return structured errors and no protected operation occurs. |
| Web middleware is the only gate | The MCP route bypasses browser middleware and reaches a tool without entitlement checks. | Apply authentication, subscription, tier, and rate-limit checks at the MCP tool boundary. Treat web middleware as additional defense only. | Call the MCP route through its real transport with an unauthenticated, ineligible, and eligible token. Confirm only the eligible call reaches the service. |
| Token requests expect JSON | A standard authorization client submits a form body and token exchange fails. | Parse `application/x-www-form-urlencoded` token requests. Validate grant type, client data, redirect URI, code verifier, and requested scopes before issuing tokens. | Exchange an authorization code with a form-encoded request. Confirm valid input succeeds and each invalid field fails without a token. |
| Unknown scopes expand access | An unrecognized or omitted scope becomes all available permissions. | Define an explicit scope allowlist. Reject unknown scopes. Give omitted scopes only the documented minimum, or reject them when no safe default exists. | Request an unknown scope and an empty scope. Confirm neither grant has broader permissions than the documented default. |
| Refresh rotation uses separate writes | A retry sees a half-rotated grant, then invalidates a valid session or accepts a reused refresh token. | Hash opaque tokens. Rotate the refresh token and update the grant in one atomic transaction. Mark the old token unusable in that transaction. | Submit concurrent refresh requests with the same token. Confirm one response succeeds, later reuse fails, and the surviving grant remains usable. |
| Rate limits use source IP | Connector traffic shares egress addresses, so one user exhausts another user's budget. | Key application rate limits by authenticated subject. Use IP limits only as a separate network-abuse control. | Send calls for distinct subjects through one simulated IP. Confirm each subject receives an independent allowance. |
| Public URLs follow the request | Reverse-proxy headers or a hostile Host header make discovery documents publish the wrong issuer or endpoint. | Build public URLs from explicit deployment configuration. Do not derive issuer, resource, or authorization URLs from request URLs or forwarded headers. | Send requests with altered Host and forwarded headers. Confirm discovery output still contains the configured public origin. |
| Discovery metadata is incomplete | A client chooses an incompatible registration path, cannot find the protected resource metadata, or never learns where to authorize. | Publish the authorization-server and protected-resource documents required by the chosen protocol. When client ID metadata is supported, declare that capability and only advertise client-authentication methods the token endpoint accepts. Implement at least one discovery mechanism, and prefer both: a 401 carrying a `WWW-Authenticate` challenge with `resource_metadata`, and the well-known protected-resource document at its path-inserted and root locations. | Fetch each discovery URL from outside the deployment. Send one request with no token. Confirm the client can reach the authorization server through the implemented mechanism, by the challenge header or by the well-known fallback. Complete authorization with the intended client flow and confirm no unintended dynamic registration occurs. |
| Authorization failure returns a success status | The server reports an authorization or scope denial as a success status carrying a structured error. The client cannot start step-up authorization, so the user sees a permanently dead tool. | Report every protocol-layer authorization failure with a status code and the challenge header. Use 401 for an absent or invalid token. Use 403 with an `insufficient_scope` challenge and the required scope for a scope failure. Use 400 for a malformed authorization request. Keep structured tool errors for business failures only. | Call a tool with a token that lacks the required scope. Confirm the response is 403 with a `WWW-Authenticate: Bearer error="insufficient_scope"` challenge, not a success status with an error body. |
| Redirect changes host | An HTTP redirect moves the client to another host and the client removes `Authorization`. | Register and publish one canonical HTTPS origin. Keep MCP, discovery, authorization, and token routes on that origin. Do not place a host-changing redirect on protected MCP paths. | Follow an authenticated request through the proxy. Confirm the final request stays on the canonical host and reaches the endpoint with authorization intact. |
| Proxy buffers the stream | The proxy delays or breaks streamed MCP responses, or removes protocol headers. | Disable response buffering for the MCP route. Configure a compatible upstream HTTP version. Preserve required protocol headers. When a route-level header rule replaces inherited headers, define the required header set explicitly. | Run a streamed tool response through the public proxy. Confirm the client receives chunks before completion and required headers arrive unchanged. |
| Origin is required | A cloud connector sends no `Origin` header and valid authenticated requests fail. | Validate `Origin` only when the header is present and when the endpoint needs that check. Do not use Origin as authentication. Enforce token, redirect URI, and PKCE checks independently. | Send equivalent authenticated calls with an allowed Origin, a rejected Origin, and no Origin. Confirm the first and last follow policy and the rejected request fails. |
| Environment loads at import time | Build, test, or static analysis imports a route before deployment configuration exists and fails before the handler runs. | Read and validate deployment configuration inside a runtime accessor. Call it from the request path. Keep module import free of required runtime environment reads. | Import the route with configuration absent. Confirm import succeeds and a request fails only with a clear configuration error. |
| Slow tool exceeds a timeout | An application, proxy, or platform stops a legitimate tool before the client limit. | Measure the slowest intended tool. Set application and proxy timeouts above that duration and below client or platform ceilings. Bound work, return progress where supported, and reject work that cannot finish within the budget. | Exercise a controlled slow path through the public deployment. Confirm it completes within every configured timeout and the client limit. |
| Inspector cannot use hosted OAuth | An inspection client cannot complete a host-restricted authorization flow, such as a client-host allow-list for client ID metadata documents, so developers mistake a local-tool limit for a server defect. | Keep an independent verification path. Use the Inspector where its authorization flow works. Otherwise script the real flow as the allowed client, per [directory readiness](directory-readiness.md#verification). | Record successful discovery, token, and tool calls for both the inspection path and the hosted-client path. |
| Verification writes to the live database | The production checkout holds the live database, so a verification run writes test rows or queues real jobs in production. | Run every verification in a separate worktree, per [directory readiness](directory-readiness.md#verification). | Confirm the verification configuration names a database and a queue prefix that differ from production. Confirm no production row or job changed. |
| Description promises an absent return | A tool description claims a return that the tool never produces. The model plans on absent data, and directory review fails. | Write each description from the real return shape. Edit the description in the same commit as the result shape. | Call each tool and compare its real result with every claim in its description. |
| Domain error falls to the catch-all | A domain error with no mapped message reaches the generic catch-all. The user sees no field, no limit, and no action, and directory review fails. | Map every domain error per [directory readiness](directory-readiness.md#errors). | Trigger each domain error through the real transport. Confirm each returns its mapped message, never the catch-all message. |
| Error names an absent action | An error message tells the user to use an action or tool that does not exist. | Name in an error only an action or tool that the deployed application provides. | Compare every action and tool that an error message names with the deployed tool registry and the application interface. |
| Result overflows the client limit | A pretty-printed text copy of `structuredContent`, or an unbounded third-party text field, pushes a result past the client limit. | Apply the payload rules in [directory readiness](directory-readiness.md#payload-and-timeouts). | Call each tool with the largest realistic record. Confirm the result stays under every client limit and each cut field carries its marker. |
| Adapter types hide identity fields | The adapter's server info type omits `title`, `websiteUrl`, or `icons`, so the plan drops them, though the adapter passes them through at runtime. | Decide field support from the adapter's runtime behavior and the protocol schema, not from its types. Use the protocol SDK's server info type when the adapter's type is narrower. | Connect a real MCP client per supported protocol revision and confirm each identity field in the server info it receives. |
| Icon route caches forever | A framework icon route sends a long-lived, immutable cache header on a URL with no version, so clients keep a stale icon after a change. | Put a content version in each cached icon URL, or serve an unversioned icon URL with a revalidating cache header. | Fetch each advertised icon and confirm a long-lived or immutable cache header appears only on a versioned URL. |
| Authentication blocks icons | Authentication middleware covers the icon paths, so a client or the directory receives a sign-in redirect or a 401, not an image. | Serve every advertised icon per [directory readiness](directory-readiness.md#connector-identity). | Fetch each advertised icon from a public network with no cookie or token. Confirm a 200 status and an image content type. |
| Icons need a rebuild | The icon files exist in the repository, but the deployed build predates them, so each advertised URL returns 404. | Generate the icon set before the build, then rebuild and redeploy. | After each deploy, fetch every advertised icon from the canonical public origin, not from a local server. |
| Reviewer seed breaks in production | The reviewer account loses access at a trial end, a second seed run duplicates records, or a seeded active entity starts real background work. | Apply the reviewer rules in [directory readiness](directory-readiness.md#reviewer-account-and-seed). | Run the seed twice and confirm one record set. End the trial and confirm reviewer access. After review, confirm no seeded entity runs background work. |
| Delivery is one large change | Security, deployment, and tool defects hide in a large diff and are hard to isolate. | Deliver reviewable phases: service-boundary audit, token persistence and discovery, transport and tool gates, deployment and proxy, connection verification, operator guidance, directory submission, then public communication. Keep each phase deployable or clearly gated. | Review each phase independently. Confirm every phase has its negative-path checks before the next phase depends on it. |
| Public copy leads implementation | Users see tools that are unavailable, unsafe, or not yet connected. | Write public copy after the deployed tool set and connection flow pass verification. Describe only supported tools, scopes, limits, and client surfaces. | Compare public copy with the deployed tool registry and run the documented connection path. Confirm every claim is observable. |
