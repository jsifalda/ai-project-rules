# Add loop-todos, an autonomous backlog worker

- New skill `loop-todos`. Manual `/loop-todos` only. It starts a self-cancelling recurring loop, and
  each firing claims exactly one open backlog entry, implements it, verifies it against the host
  project's own gates, closes it, updates stale docs, and commits locally. It never pushes.
- Why: `setup-todo-backlog` creates and formats a backlog and nothing consumes it. This is the
  consumer. It also makes a defect found mid-session outlive the session in a way that actually gets
  worked, rather than only recorded.
- The ledger, not the backlog file, is the authority on run state. It lives under the shared git
  common dir, keyed per working tree, so it can never be staged into a commit and two worktrees of
  one repo cannot join each other's run. Everything a later firing needs to recover reads from it.
- The `in progress` status line is a deliberate fourth value in a vocabulary `setup-todo-backlog`
  fixes at three. It is a breadcrumb for a human reading `git diff`, transient and uncommitted, and
  no step recovers state from it. That containment is stated in the skill because a reader who knows
  the three-state rule would otherwise delete the line as a bug.
- An entry that is underspecified stops the loop rather than being guessed at or skipped. That was a
  deliberate call over parking it and moving on. Guessing at loop speed produces wrong work faster
  than anyone reviews it.
- Written against an adversarial dry-run over a real 20-entry backlog and a real 9-gate verification
  protocol. That pass found five contract-breaking holes, all of which shaped the final design: the
  claim went blind once an entry was closed but uncommitted, an answered question had no route back
  into the work, run staleness was measured against a timestamp that never advances, the steps before
  the claim held no lock, and one shared ledger let separate worktrees collide.
- Indexed in `README.md`. No new dependency.
